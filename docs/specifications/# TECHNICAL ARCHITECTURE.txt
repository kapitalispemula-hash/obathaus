# 1. ARCHITECTURE OBJECTIVE

Technical Architecture bertujuan menentukan struktur teknis aplikasi Cafe POS agar:

1. Seluruh fitur memiliki alur komunikasi yang jelas.
2. Frontend dan backend memiliki tanggung jawab masing-masing.
3. Keamanan data berdasarkan role diterapkan secara konsisten.
4. Proses checkout aman dari transaksi ganda.
5. HPP dan keuntungan dihitung secara akurat.
6. Aplikasi dapat digunakan melalui HP, tablet, dan desktop.
7. Deployment dapat dilakukan melalui GitHub dan Vercel.
8. Sistem mudah dikembangkan tanpa harus membangun ulang seluruh aplikasi.

## 1.1 Architecture Principles

Gunakan prinsip:

- Separation of Concerns.
- Server-side Security.
- Database as Source of Truth.
- Atomic Transaction Processing.
- Role-Based Access Control.
- Reusable Components.
- Type Safety.
- Mobile-First.
- Environment Separation.
- Maintainable Codebase.

Jangan menempatkan seluruh business logic di frontend.

1. Pengguna membuka aplikasi.
2. Next.js menampilkan halaman.
3. Pengguna login melalui Supabase Auth.

5. Server mengambil role dari profil pengguna.

7. Pengguna melakukan aktivitas.
8. Request dikirim melalui jalur server atau Supabase client yang telah dibatasi RLS.
9. PostgreSQL memvalidasi dan memproses data.

# 5. FRONTEND ARCHITECTURE

## 5.1 Server Components

Gunakan Server Components sebagai default.

Cocok untuk:
- Dashboard data awal.
- Daftar produk Admin.
- Riwayat transaksi.
- Detail transaksi.
- Rekap keuangan.
- Pengaturan.

Keuntungan:
- Mengurangi JavaScript di browser.
- Data dapat diambil secara server-side.
- Mengurangi paparan data sensitif.

## 5.2 Client Components

Gunakan Client Components untuk interaksi yang membutuhkan state browser.

Cocok untuk:
- Keranjang POS.
- Product search.
- Quantity control.
- Payment modal.
- Cash calculator.
- Interactive charts.
- Form input.
- Toast dan modal.

Jangan menambahkan `"use client"` pada seluruh halaman jika hanya beberapa komponen yang membutuhkan interaksi.

## 5.3 Feature-Based Architecture

Setiap fitur memiliki:
- Components.
- Types.
- Schemas.
- Services.
- Hooks jika diperlukan.

Contoh:

```text
features/
└── pos/
    ├── components/
    ├── schemas/
    ├── services/
    ├── hooks/
    └── types/
```

Tujuannya agar perubahan pada POS tidak merusak fitur laporan atau manajemen produk.

# 6. SUPABASE CLIENT ARCHITECTURE

Gunakan pemisahan client dan server.

## 6.1 Browser Client

Digunakan untuk kebutuhan browser yang memang memerlukan interaksi langsung.

Contoh:
- Auth session client.
- Realtime subscription jika diperlukan.
- Operasi publik yang aman.

File:

`src/lib/supabase/client.ts`

## 6.2 Server Client

Digunakan untuk:
- Mengambil session pengguna.
- Mengakses database sesuai identitas pengguna.
- Memvalidasi authorization.
- Menjalankan operasi server-side.

File:

`src/lib/supabase/server.ts`

Gunakan konfigurasi SSR Supabase yang sesuai dengan versi package terpasang.

Jangan membuat pola client/server sendiri yang mengabaikan mekanisme cookie dan refresh session.

## 6.3 Admin/Service Role Client

Buat client khusus server untuk operasi administratif yang membutuhkan Service Role.

Aturan:
- Tidak boleh diimpor ke Client Component.
- Tidak boleh diekspos melalui browser.
- Tidak boleh menggunakan prefix `NEXT_PUBLIC_`.
- Hanya digunakan setelah pemeriksaan otorisasi server.
- Jangan menggunakan Service Role untuk operasi biasa yang dapat dilakukan melalui RLS.

# 7. AUTHENTICATION & AUTHORIZATION

## 7.1 Authentication Flow

```mermaid
flowchart TD
    A[Open Application] --> B[Login]
    B --> C[Supabase Auth]
    C --> D{Valid Session?}
    D -->|No| E[Show Login Error]
    D -->|Yes| F[Load User Profile]
    F --> G{Account Active?}
    G -->|No| H[Access Denied]
    G -->|Yes| I{User Role}
    I -->|Admin| J[Admin Dashboard]
    I -->|Cashier| K[POS]
```

## 7.2 Role Authorization

Role utama:

- admin
- cashier

Pemeriksaan role dilakukan:
1. Pada server.
2. Pada API atau Server Actions.
3. Pada database menggunakan RLS.

Frontend hanya mengatur tampilan dan navigasi, bukan menjadi sumber keamanan utama.

## 7.3 Route Protection

Admin route:
- `/admin/*`

Cashier route:
- `/pos/*`

Jika Kasir mencoba membuka `/admin/reports`, server harus menolak akses.

Jika Admin membuka `/pos`, sistem dapat mengizinkan akses sesuai kebijakan aplikasi, tetapi Admin tetap tidak boleh kehilangan akses dashboard Admin.

## 7.4 Session Handling

- Gunakan session Supabase.
- Refresh session sesuai mekanisme resmi SSR.
- Redirect saat session berakhir.
- Jangan menyimpan password dalam localStorage.
- Jangan menyimpan Service Role Key di browser.
- Jangan mempercayai role yang dikirim client.

# 8. API & SERVER ACTION ARCHITECTURE

Gunakan Server Actions atau Route Handlers sesuai kebutuhan.

Rekomendasi:

**Server Actions**
- Operasi form internal.
- CRUD produk.
- CRUD kategori.
- CRUD pengeluaran.
- Perubahan pengaturan.

**Route Handlers**
- Operasi yang membutuhkan endpoint HTTP eksplisit.
- Integrasi eksternal.
- Export laporan.
- Endpoint khusus PWA bila diperlukan.

**PostgreSQL RPC**
- Checkout atomic.
- Void transaksi.
- Refund.
- Perhitungan laporan kompleks yang memerlukan konsistensi database.

Jangan membuat API route untuk setiap query sederhana jika server component dapat mengambil data dengan aman.

## 8.1 API Modules

Gunakan schema validation, misalnya Zod.

Contoh validasi:
- Product ID.
- Quantity.
- Nominal.
- Discount type.
- Payment method.
- Date range.
- User role.
- Store ownership.

Jangan hanya memvalidasi form di browser.

# 9. BUSINESS LOGIC ARCHITECTURE

Business logic harus memiliki sumber kebenaran yang jelas.

| Business Logic | Sumber Kebenaran |
|---|---|
| Harga produk | PostgreSQL |
| HPP produk | PostgreSQL |
| Total transaksi | Checkout RPC |
| Snapshot transaksi | PostgreSQL |
| Nomor invoice | Invoice counter RPC |
| Status transaksi | PostgreSQL |
| Refund | Refund RPC |
| Void | Void RPC |
| Laporan keuangan | Reporting SQL |
| Hak akses | RLS + Server Authorization |

## 9.1 Checkout Flow

```mermaid
sequenceDiagram
    participant C as Cashier
    participant UI as POS Frontend
    participant S as Next.js Server
    participant DB as PostgreSQL RPC

    C->>UI: Select Products
    UI->>UI: Build Cart
    C->>UI: Checkout
    UI->>S: Submit Checkout
    S->>S: Validate Session and Role
    S->>DB: complete_checkout()
    DB->>DB: Validate Products and Prices
    DB->>DB: Calculate Discount and Tax
    DB->>DB: Create Invoice
    DB->>DB: Save Transaction and Items
    DB->>DB: Save Payment
    DB-->>S: Transaction Result
    S-->>UI: Success Response
    UI-->>C: Show Receipt
```

Aturan penting:
- Harga dan HPP tidak dipercaya dari frontend.
- Database menghitung ulang total.
- Checkout harus atomic.
- Idempotency key harus digunakan.
- Keranjang tidak dihapus sebelum konfirmasi berhasil.

## 9.2 Void Flow

1. Admin membuka detail transaksi.
2. Admin memilih Void.
3. Sistem meminta alasan.
4. Server memvalidasi role.
5. RPC memvalidasi status transaksi.
6. Database memperbarui status menjadi voided.
7. Audit log dibuat.
8. Transaksi tidak lagi masuk laporan penjualan.

## 9.3 Refund Flow

1. Admin membuka transaksi.
2. Admin memilih Refund.
3. Admin memilih item dan jumlah.
4. Sistem menghitung nilai refund berdasarkan snapshot.
5. Server memvalidasi jumlah yang belum direfund.
6. RPC menyimpan refund.
7. Database memperbarui status transaksi.
8. Laporan memperhitungkan pengurangan penjualan dan HPP.

Refund harus atomic dan tidak boleh melebihi jumlah barang yang belum direfund.

# 10. POS STATE MANAGEMENT

Keranjang POS merupakan state utama yang harus responsif.

State minimal:

```text
cartItems
selectedCategory
searchQuery
discountType
discountValue
paymentMethod
cashReceived
isCartOpen
isCheckoutLoading
checkoutError
```

Aturan:

- State keranjang dapat dikelola melalui React state atau state management library yang ringan.
- Keranjang tidak boleh menjadi sumber kebenaran nominal transaksi.
- Harga final dihitung ulang di server/database.
- Saat produk berubah menjadi tidak tersedia, checkout harus ditolak dengan pesan yang jelas.
- Saat checkout berhasil, keranjang dibersihkan.
- Saat checkout gagal, keranjang dipertahankan.

Jangan menyimpan HPP ke state browser Kasir.

Jangan menghitung seluruh laporan menggunakan array transaksi yang diunduh ke browser.

Gunakan SQL views atau RPC reporting functions.

Laporan minimal:
- Daily sales.
- Weekly sales.
- Monthly sales.
- Yearly sales.
- Product performance.
- Payment summary.
- Expense summary.
- Profit summary.

```mermaid
flowchart TD
```

## 11.3 Financial Security

Endpoint laporan harus memvalidasi Admin.

Kasir tidak boleh mendapatkan:
- Net HPP.
- Gross Profit.
- Net Operating Profit.
- Net Profit Margin.
- Expense Summary.

## 12.2 Security

- Validasi MIME type.
- Batasi ukuran file.
- Batasi akses upload berdasarkan role.
- Gunakan path berdasarkan store.
- Bukti pengeluaran tidak boleh publik secara default.
- Hindari mengandalkan nama file dari pengguna sebagai nama objek final.

# 13. RECEIPT PRINT ARCHITECTURE

Struk menggunakan HTML dan CSS khusus print.

Gunakan:
- Printable receipt component.
- Print stylesheet.
- CSS `@media print`.
- CSS `@page`.

Ukuran:
- 58mm.
- 80mm.

Alur:
1. Checkout berhasil.
2. Server mengembalikan ID transaksi.
3. Aplikasi mengambil data struk yang diizinkan.
4. Printable receipt dirender.
5. Browser membuka dialog cetak.
6. Kasir memilih printer.

Catatan:
- Jangan membuat transaksi baru saat cetak ulang.
- Jangan mencetak HPP.
- Jangan mengandalkan tampilan layar sebagai satu-satunya layout struk.
- Uji hasil cetak pada browser dan printer thermal yang digunakan.

Cache:
- Static assets.
- App shell.
- Icon.
- Font.

Jangan cache secara sembarangan:

- Response laporan keuangan.

- Berikan pesan agar pengguna kembali online.

# 17. SECURITY ARCHITECTURE

Keamanan harus diterapkan pada beberapa lapisan.

## 17.1 Frontend

- Route navigation berdasarkan role.
- Validasi input.
- Error handling.
- Tidak menampilkan informasi sensitif.
- Tidak menyimpan secret.

## 17.2 Server

- Validasi session.
- Validasi role.
- Validasi store.
- Validasi input.
- Rate limiting untuk endpoint sensitif.
- Error response aman.

## 17.3 Database

- RLS.
- Foreign key.
- Constraints.
- Atomic RPC.
- Snapshot transaksi.
- Audit logs.
- Privilege separation.

## 17.4 Critical Security Rules

1. Kasir tidak dapat mengakses HPP.
2. Kasir tidak dapat mengakses laporan keuangan.
3. Kasir tidak dapat mengubah role.
4. Kasir tidak dapat melakukan void.
5. Kasir tidak dapat melakukan refund.
6. User tidak dapat mengakses store lain.
7. Checkout tidak mempercayai nominal frontend.
8. Service Role Key tidak boleh bocor.
9. Data historis transaksi tidak boleh dimodifikasi sembarangan.
